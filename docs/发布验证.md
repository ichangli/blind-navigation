## 三维样式修复

用户提供的控制台日志确认，原演示请求 vendor/arcgis/esri/themes/dark/main.css，返回 404。npm 版显示库实际文件位于 vendor/arcgis/esri/assets/esri/themes/dark/main.css，已修正构建路径。旧的二维回退提示把所有初始化失败写成“当前设备未启用三维”，已改为不推断硬件能力的提示，并保留加载失败原因。生成的脚本和样式链接附内容版本号，以更新浏览器缓存。

这是已定位并修复的资源路径问题；用户当前设备的三维画面仍需刷新页面后确认，不能用资源 HTTP 200 或 JSDOM 测试代替实机渲染结论。

自托管 AMD 的 Worker loader、RemoteClient 和包路径也已显式配置为站内已有文件，并在 AMD 模块执行前设置 assetsPath；新增检查覆盖样式、loader 和 Worker 入口，防止沿用 CDN 布局中的缺失文件路径。

## 三维模块 503 与加载方式调整

用户刷新后的日志显示 SSAO.js 返回 HTTP 503，随后地图库超时。当前网络连续三次读取该文件均为 200，只能证明文件存在，不能排除用户链路或服务节点的临时故障。原来的 AMD 冷启动需要逐个加载大量模块，一次请求失败就可能阻止依赖树完成。

构建现在将 loader 未内置的 4,097 个 AMD 模块注册为一个带内容哈希的模块缓存，约 17.33 MiB（本地 gzip 约 4.07 MiB）。主线程在 require SceneView 之前载入缓存，Worker 也使用同一缓存；原始 vendor 文件和版权声明完整保留。样式、loader 和缓存脚本遇到加载错误最多重试两次；总等待上限为 120 秒。SDK 超时后才完成时，允许从二维回退恢复三维。

实际模块测试已加载原 SDK 的 SceneView、SSAO、GeoJSONLayer 及页面其余入口，未发出逐模块脚本请求。Worker 测试运行原 loader、缓存和 RemoteClient，验证 URL 入口与 AMD 模块指向同一构造函数，避免重复初始化 kernel。测试仍使用 JSDOM / JavaScript 上下文，尚未验证 GPU 绘制，不能将其称为三维画面验收通过。
